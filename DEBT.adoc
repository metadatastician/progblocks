== How to read this

[cols="1,4"]
|===
| *OPEN* | Confirmed by evidence recorded here. Needs doing.
| *FLAG-ONLY* | Confirmed, but may not be fixed unilaterally (licence changes, upstream-owned files). Recorded, not actioned.
| *ACCEPTED* | A real limitation, deliberately not being fixed for now. Not a TODO.
| *CLEARED* | Fixed or removed. Kept, with the date and the evidence, so the history stays readable.
|===

Severity reflects consequence, not effort.

== Licence debt

=== L1 — Version metadata disagreed across four files *(CLEARED 2026-10-05)*

`package.k9` and `contracts.ncl` declared `1.0.0`; `progblocks.launcher.a2ml` and
`progblocks-launcher.sh` declared `0.1.0`; `package.json` declared `0.3.0`. The owner
chose `0.3.0`, and every one of those fields now says it. Nothing has been released;
`0.3.0` is a pre-release number.

Evidence: `grep -rn "1\.0\.0\|0\.1\.0\|0\.3\.0" package.k9 contracts.ncl progblocks.launcher.a2ml package.json`

=== L2 — `progblocks.launcher.a2ml` licence was changed without upstream coordination *(FLAG-ONLY)*

The file previously declared `CC-BY-SA-4.0` while the rest of the repo was MPL-2.0. PR #15
aligned it to MPL-2.0 on the reasoning that a launcher config is code, not content. If
`launch-scaffolder` generates these files from a template that assumes CC-BY-SA, the
change will be reverted on the next regeneration.

Evidence: `head -20 progblocks.launcher.a2ml`; the file's own header names
`launcher-standard_praxis.deed v0.4.0` as its governing spec.

Clearing it: confirm the licence expectation with the `launch-scaffolder` standard, then
either keep MPL-2.0 or restore CC-BY-SA-4.0 with a documented rationale.

== Code debt

=== C1 — Cross-site scripting via unescaped re-injection *(CLEARED 2026-10-05, branch `feat/render-core-variants-vars`)*

*Cleared.* `src/prog-block.js` was rewritten to build its shadow tree once with
`createElement` and patch it in place. Variant source is read with
`template.content.textContent` (so unescaped tags in a template are dropped, never
rendered), and every piece of author or reader text — code, tab labels, variable names,
typed values — reaches the shadow tree through `textContent`. There is no `innerHTML`
assignment anywhere in `src/`. Evidence: `grep -n innerHTML src/` → one hit, the explanatory
header comment in `src/prog-block.js`; the `untrusted content is never rendered as markup`
group in `tests/component.test.js` (four tests: escaped markup in a variant, unescaped
markup in a template, markup in a typed value, markup in a tab label) passes under
`bun test`. Those tests run under happy-dom, not in a real browser.

The original finding, kept for the record:

Variant content is read with `t.innerHTML` (`src/prog-block.js:60`) and re-injected as
HTML (`:199`); variable values are interpolated unescaped into an attribute,
`value="${val}"` (`:165`). There is no escaping anywhere in the component. A variable
value of `" onfocus="…` performs attribute injection, and markup inside a code block is
executed as markup instead of displayed as code.

This matters more than its line count suggests: the component's stated purpose is
rendering code snippets in documentation and wikis — that is, content authored by people
other than the page owner.

Evidence: `grep -n "innerHTML\|value=\"\${" src/prog-block.js`

Clearing it (as done): build the DOM with `createElement` + `textContent` / `.value`
instead of string concatenation.

=== C2 — Every keystroke destroys the focused input *(CLEARED 2026-10-05)*

*Cleared* by the same rewrite: the variable `<input>` elements are created once, and an
`input` event updates only the `<span>` nodes for that variable in the code panel. Evidence:
`tests/component.test.js` › `typing keeps the same input element and updates the code in
place` (asserts the same node before and after typing). Not observed in a real browser.

The original finding, kept for the record:

Editing a variable calls `updateState`, which rewrites `shadowRoot.innerHTML` wholesale
(`src/prog-block.js:95-99` → `:49-52` → `:177`). The `<input>` being typed into is
destroyed and recreated on each character, so focus and caret are lost. Multi-character
variable values are effectively untypeable — the headline interactive feature does not
survive contact with a user.

Evidence: `sed -n '95,99p;49,52p;177p' src/prog-block.js`

Clearing it: targeted DOM updates — variable input events update only the rendered
output node; inputs are rebuilt only when the variant changes.

=== C3 — The editor destroys the variant template *(CLEARED 2026-10-05 — feature removed)*

*Cleared by removal.* The `contenteditable` code editor was removed as out of charter
(ProgBlocks renders examples; it is not an editor). The variant source is now immutable
after it is read. Evidence: `grep -n contenteditable src/` → nothing.

The original finding, kept for the record:

Typing in the editor overwrites the variant source with post-interpolation text,
permanently losing `{{ variables }}`. The code says so itself: *"Careful: if A2ML vars
exist, typing over them destroys the template tag!"*

Evidence: `sed -n '234,242p' src/prog-block.js`

Clearing it: keep the raw variant template as the source of truth; the editor edits raw
source and the preview re-interpolates.

=== C4 — Falsy variable values render as raw placeholders *(ACCEPTED 2026-10-05 — now deliberate)*

*Re-assessed 2026-10-05.* The rewrite keeps `||` semantics on purpose: an empty value means
"not set", so the block shows the inline default if there is one, otherwise `{{ name }}`
styled `.unset` (`_resolve` and `_renderValues` in `src/prog-block.js`). A variable cannot
be deliberately set to the empty string. Correction to the original entry: `"0"` is a
non-empty string and therefore truthy, so it was never affected and is substituted
normally.

The original finding, kept for the record:

`this._state.variables.get(key) || match` (`src/prog-block.js:91`) falls back to the
literal `{{ key }}` whenever the value is falsy, so a variable deliberately set to `""`
or `"0"` displays as its own placeholder.

Evidence: `sed -n '91p' src/prog-block.js`

Clearing it: `variables.has(key) ? variables.get(key) : match`.

=== C5 — Variables accumulate across variant switches *(CLEARED 2026-10-05 — superseded by design)*

*Superseded.* Variables are now collected once, from every variant, when the element first
connects; the block shows one labelled input per variable for its whole life, and values
persist across variant switches. That union is the intended behaviour, not drift. Evidence:
`tests/component.test.js` › `values persist across variant switches and one input serves
all variants`.

The original finding, kept for the record:

`extractA2MLVariables` (`src/prog-block.js:76-86`) merges into the existing map and never
prunes. Switching variants leaves every variable from every previously visited variant in
the state map and in the rendered controls.

Evidence: `sed -n '76,86p' src/prog-block.js`

Clearing it: rebuild the variable map per variant, preserving values only for keys the
new variant actually declares.

=== C6 — Shadow stylesheet path breaks the component's core promise *(CLEARED 2026-10-05)*

*Cleared.* The stylesheet URL is now `new URL('./prog-block.css', import.meta.url)`
(`STYLESHEET_URL` in `src/prog-block.js`), so it resolves against the module, not the host page. Evidence:
`tests/component.test.js` › `stylesheet resolves against the module, not the host page`,
which mounts the block on a page at `/docs/deep/page.html` under happy-dom. Not yet
exercised in a real browser at a non-root depth.

The original finding, kept for the record:

The shadow root loads `<link rel="stylesheet" href="./src/prog-block.css">`
(`src/prog-block.js:178`), which resolves against the *document* URL, not the module URL.
The component is therefore styled correctly only when the consuming page sits exactly one
directory above `src/`. The README promises injection into arbitrary static-site
generators and wikis; this line makes that false for almost all of them.

Evidence: `sed -n '178p' src/prog-block.js`

Clearing it: `new URL('./prog-block.css', import.meta.url)`, or adopt a constructable
stylesheet, or inline the CSS into the shadow root.

=== C13 — The generated launcher cannot start the server *(FLAG-ONLY — upstream)*

`progblocks-launcher.sh` is generated by `launch-scaffolder` and marked "do not edit". As
generated it cannot work:

* a blank line precedes the `#!/usr/bin/env bash` shebang, so the kernel will not exec it directly;
* `REPO_DIR=""` is never populated, so `cd "$REPO_DIR"` silently no-ops;
* `ICON_SOURCE="/assets/icon-256.png"` is an absolute path at the filesystem root, and the file does not exist anywhere;
* the startup-command search requires `[ -x "$candidate" ]`, which is false for strings such as `"python3 -m http.server"`, so `START_COMMAND` is **always empty** and `start_server` always dies with "No startup command found";
* absolute paths from the author's machine (`/home/hyperpolymath/…`, `/var/mnt/eclipse/…`) are baked into every generated `.desktop` entry.

The source config `progblocks.launcher.a2ml` is *correct* on every one of these points —
it uses `{repo-dir}` tokens and XDG paths. The generator lost them.

Evidence: `head -1 progblocks-launcher.sh | cat -A` (blank first line);
`grep -n 'REPO_DIR=\|ICON_SOURCE=\|-x "$candidate"' progblocks-launcher.sh`

Clearing it: file the defect against `launch-scaffolder` and regenerate. **Do not
hand-edit the generated file** — it affects every generated launcher in the estate, so
fixing it here would hide an estate-wide bug behind one repo's patch.

=== C14 — Light-DOM changes after first connect are not observed *(CLEARED 2026-10-05, branch `feat/persist-and-live-content`)*

*Cleared.* `connectedCallback()` now attaches a `MutationObserver` to the host (`childList`,
`subtree`, `characterData`, and the `data-variant` attribute). A mutation schedules
`refresh()`, coalesced to one rebuild per microtask; `refresh()` re-reads the light DOM,
replaces the shadow tree, and restores the selected variant by name and the reader's
variable values. The observer disconnects in `disconnectedCallback()`. Evidence:
`tests/component.test.js` › `authored content that changes after render` (4 tests:
`replacing templates re-renders, keeping the variant and reader values`, `editing
plain-text content is picked up`, `refresh() picks up edits inside template.content`, `a
burst of mutations triggers one rebuild`). Mutation-checked by hand on 2026-10-05:
disabling the observer failed 3 of them. Under happy-dom; also checked once by hand in headless Chromium on 2026-10-05 (a live template
swap kept the variant and the typed value).

Caveats that remain: an edit to a `<template>`'s `.content` fragment is invisible to any
observer, so the host must call the public `refresh()` method after one; and a rebuild
replaces the variable inputs, so focus inside the block is lost when authored content
changes (host-driven, rare).

The original finding, kept for the record:

The authored `<template data-variant>` children (or the element's own text) are read once,
in the first `connectedCallback`. Adding, removing or editing templates afterwards — for
example by a client-side router or a CMS preview that patches the DOM in place — has no
effect on the rendered block. Re-connecting the element does not re-read either, because
`_built` stays `true`.

Evidence: `grep -n "_built" src/prog-block.js` (the guard in `connectedCallback()` around
`_readLightDom()`).
No `MutationObserver` or `slotchange` listener exists in `src/`.

Clearing it: observe the light DOM and rebuild the variant list and variable inputs when it
changes, preserving entered values for variables that survive. Until then, hosts must
replace the whole `<prog-block>` element to change its content.

=== C15 — Variant-group selection is not persisted *(CLEARED 2026-10-05 — opt-in `persist`)*

*Cleared* as an opt-in. With the boolean `persist` attribute (effective only together with
`group`), a reader-initiated selection is stored in `localStorage` under
`progblocks:variant:<group>` and restored on the next page load, ahead of the `variant`
attribute. Programmatic selections are not stored. Every storage access is in
`try`/`catch`, so blocked or unavailable storage degrades silently to page-local group
sync; a remembered name the block lacks leaves the first variant selected. Without
`persist` nothing is stored, which keeps the original host-policy reasoning below intact
as the default. Since 2026-10-05 other open tabs of the same site follow through the `storage` event.
Evidence: `tests/component.test.js` › `remembering the reader's variant` (6 tests). Mutation-checked
by hand on 2026-10-05: removing the persist write failed 1 of them.

The original finding, kept for the record:

`group="name"` keeps every block on the page with that group on the same variant, but the
registry is an in-memory `Map` (`const groups` in `src/prog-block.js`). The choice is lost on navigation or
reload, and blocks on other pages start from their own `variant` attribute or first variant.

Evidence: `grep -n "localStorage\|sessionStorage" src/prog-block.js` → nothing.

Accepted for now: persistence is a host-page policy decision (storage consent, key naming),
and the `progblocks:variant-change` event plus the `variant` property let a host persist
and restore the choice itself.

=== C16 — No syntax highlighting *(ACCEPTED, added 2026-10-05)*

The component renders code as plain text. It does not tokenise or colour any language, and
`.machine_readable/contractiles/intend/Intentfile.a2ml` lists "a syntax highlighter" as an
anti-purpose. What it provides for a host highlighter: the `language` attribute becomes a
`language-*` class on the inner `<code>`, and the shadow parts `header`, `tab`,
`copy-button`, `variables`, `code` and `variable` are exposed for `::part()` styling.

Evidence: `grep -n "language-\|part:" src/prog-block.js`.

Not verified: no external highlighter has been tried against the shadow tree. A highlighter
that rewrites `<code>` content with markup would also replace the variable `<span>` nodes,
so the integration is not a drop-in; this is a design question, not yet a tested path.

=== T3 — No accessibility testing of any kind *(OPEN — gaps fixed, verification still missing)*

*Update 2026-10-05.* The specific gaps listed below were fixed in the render-core rewrite:
the tablist follows the WAI-ARIA tabs pattern (`role` tab/tablist/tabpanel,
`aria-controls`/`aria-labelledby`, roving `tabindex`, ArrowLeft/ArrowRight with wrap,
Home/End, automatic activation); the `opacity: 0.7` on inactive tabs was removed and
selection is shown by an underline bar plus weight; every variable input has a `<label>`,
inside a `<fieldset>` with a visually hidden legend; a `role="status"` region announces the
copy and download results; `:focus-visible` rings and a `forced-colors` block exist; line numbers are
`aria-hidden`; the code panel is focusable (`tabindex="0"`) for keyboard scrolling. The
structural parts are asserted in `tests/component.test.js` under happy-dom.

*Update 2026-10-05.* `just a11y` (`tools/a11y-audit.mjs`) runs axe-core (WCAG 2.0/2.1/2.2 A+AA
and best practice) on `index.html` in headless Chromium, dark and light: 0 violations, 0 needing
review, contrast passing on 39 nodes (38 before the demo gained `persist`). Its one earlier finding (`aria-label` on a role-less `<pre>`)
was fixed with `role="group"`. Planted defects make it exit 1. Since 2026-10-05 the `build` job in `ci.yml` also runs it on every push and PR, against the runner's Google Chrome.

What is still missing, and why this entry stays open: no screen-reader session, and axe checks
only resting states of the default palette. The status region announces only copy and download results:
a variant change driven by `group` sync in *another* block is not announced. AA remains a
target, not a verified level.

The original finding, kept for the record:

The repository claims a WCAG 2.1 AA *target* and carries real ARIA attributes, but nothing
tests them. Known gaps against AA/APG for a tablist: no roving `tabindex` or arrow-key
navigation, no `tabpanel` + `aria-controls` pairing, no `aria-live` announcement for
variant or export state changes, and inactive tabs at `opacity: 0.7` degrade contrast.
Focus destruction (C2) is itself an accessibility defect, not merely a usability one.

Evidence: `grep -rn "aria-\|role=" src/prog-block.js` shows the attributes present;
`grep -rln "axe\|pa11y\|aria" tests/` returns nothing.

Clearing it: add an automated accessibility check (done 2026-10-05 as `just a11y`, run in CI), and test with at least one real screen reader. The tablist keyboard model was fixed
on 2026-10-05.

== Governance debt

The `Optimus-Branch` ruleset protects `main`. Four of its requirements were failing on every
pull request, so every merge needed an administrator bypass — and a bypass that is *always*
required stops being a safeguard and becomes a formality.

The four split cleanly into two kinds, and the distinction decides the treatment:

[cols="1,3"]
|===
| *Unmeetable* | No possible pull request could satisfy it, however good the code. Keeping it does not raise quality; it only makes bypass mandatory. **Fixed** — G1, G4.
| *Unmet* | Satisfiable, but not by this repository yet. Removing it would launder a real deficiency into a green board. **Kept** — G2, G3.
|===

=== G1 — Code-owner review was structurally impossible *(CLEARED 2026-08-07)*

The ruleset set `required_approving_review_count: 0` but `require_code_owner_review: true`.
`CODEOWNERS` assigns every path to `@hyperpolymath`, who is also the author of every pull
request. GitHub refuses self-approval outright ("Can not approve your own pull request"), so
**no PR could ever satisfy the rule**. Not a misconfiguration of degree — a requirement with
no satisfying assignment.

`require_code_owner_review` is now `false`. The automated gates are untouched: signatures,
CodeQL code-scanning, code-quality, coverage, the merge queue and the required status checks
all still apply. What was removed is a human-review requirement that no human could give.

Evidence: `gh api repos/metadatastician/progblocks/rulesets/19619017` — the rule reads
`false`; all 11 rules and 11 bypass actors verified intact after the change.

If a second maintainer ever joins, re-enabling this is the right move — the rule is sound,
it was only unsatisfiable for a solo repository.

=== G2 — Required check `SonarCloud Code Analysis` is failing on a real defect *(OPEN)*

SonarCloud is a required status check and reports *Security Rating C on new code* (required
≥ A). It was already failing on `main` before this work began.

**Deliberately not removed from the ruleset.** A C security rating on a component with an

The gate is scoped to *new code*, which sharpens the diagnosis: it **passes** on a

=== H4 — Several contractile probes were unrunnable as written *(CLEARED 2026-08-07)*

first match and SIGPIPEs the command upstream, and pipefail then reports that death as the
pipeline's status.

Recorded rather than silently fixed because the failure mode is instructive: a *reporting*
tool that invents failures is the same class of defect as a *gate* that cannot fail. Both
decouple the signal from the truth.

Evidence: `just probes` → 36 pass, 0 fail; each security probe confirmed non-vacuous by
planting a violation (a fake token in `src/`, a `.pem` file at the root) and observing the
corresponding probe fail, then clear on removal.
