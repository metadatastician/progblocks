== Before you start

[IMPORTANT]
====
Read link:Feature-Status.adoc[Feature Status] first. This page describes
how to use `<prog-block>` as it actually behaves. There is currently no
build step and no package publish. The behaviour below is unit-tested
under happy-dom (`bun test`) but has not been checked in a real browser
during the 2026-10-05 review. Verify against the checked-out source
before you rely on any of this.
====

== Minimal usage

Load the module and drop the element into your page:

[source,html]
----
<script type="module" src="./src/prog-block.js"></script>

<prog-block line-numbers group="os">
  <template data-variant="macOS">
    brew install {{ package = ripgrep }}
  </template>
  <template data-variant="Linux">
    sudo apt-get install {{ package = ripgrep }}
  </template>
</prog-block>
----

Template content is dedented, so it can be indented to match the
surrounding HTML. Write it as you would inside `<pre>`: escape `<` as
`&lt;` and `&` as `&amp;`. Unescaped tags are dropped, never rendered.

`customElements.define('prog-block', ProgBlock)` runs at the bottom of
`src/prog-block.js` when the module loads; `tests/registration.test.js`
verifies this. If the module ever fails to load, no `<prog-block>`
element on the page would upgrade; each would stay inert, unstyled,
plain HTML.

== Embedding at any page depth

Until 2026-10-05 the shadow root loaded `<link href="./src/prog-block.css">`,
a document-relative path that only resolved for a host page sitting one
level above `src/`. That limitation is fixed: `src/prog-block.js` now
resolves the stylesheet against its own module URL,

[source,javascript]
----
new URL('./prog-block.css', import.meta.url)
----

so `prog-block.css` only has to sit next to `prog-block.js`, wherever the
host page lives. Keep the two files together when you vendor them into
another site's asset pipeline.

How strongly this is known: `tests/component.test.js` › `stylesheet
resolves against the module, not the host page` mounts the element on a
page at `/docs/deep/page.html` under happy-dom and checks the resolved
URL. It has not yet been checked in a real browser at a non-root depth,
nor inside `ddraig-ssg`, BerryWiki or any other consumer.

Two other things to know before embedding:

* Since 2026-10-05 the element re-renders when your site changes its
  content after it has rendered (before then it read its templates once).
  If your code edits a `<template>`'s `.content` fragment directly, call
  `block.refresh()` afterwards: no observer can see that change.
* The element stores nothing unless you add `persist` to a block that has
  a `group`; then the reader's chosen variant name is kept in
  `localStorage` under `progblocks:variant:<group>`. See
  link:Authoring-Blocks.adoc[Authoring Blocks].
* There is no syntax highlighting. The `language` attribute becomes a
  `language-…` class on the inner `<code>`, and parts (`::part(code)`,
  `::part(variable)` and others) are exposed for styling.
