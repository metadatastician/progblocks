== The authoring model

Content goes inside `<prog-block>` as one or more light-DOM
`<template>` children, each carrying a `data-variant` attribute:

[source,html]
----
<prog-block line-numbers label="Shell">
  <template data-variant="bash">
    echo "Hello, {{ name = world }}"
  </template>
  <template data-variant="nushell">
    echo $"Hello, ({{ name = world }})"
  </template>
</prog-block>
----

`_readLightDom()` reads every direct `template[data-variant]` child's
`content.textContent`, dedents it (common indentation and blank first
and last lines are stripped), and builds one tab per template. If there
are no `<template>` children, the element's own text becomes a single
variant with no tablist; the `language` attribute is then shown as its
label.

Write example code the way you would inside `<pre>`: escape `<` as
`&lt;` and `&` as `&amp;`. Tags written unescaped inside a `<template>`
are parsed by the browser as template DOM and dropped from the text — they
are never rendered as markup.

Variant tabs are **generic**: the `data-variant` string is just a label.
There is no platform auto-detection. Use:

* `variant="Name"` to choose the initially selected variant (also a
  read/write `variant` property);
* `group="name"` to keep every block on the page with the same group on
  the same variant name. By default the choice is in memory only;
* `persist` (with `group`) to remember the reader's choice across page
  loads. The variant name the reader selects is stored in `localStorage`
  under `progblocks:variant:<group>` and restored on the next load, ahead
  of `variant`. Only the name is stored, and only for selections the
  reader makes. If storage is blocked, the group still syncs within the
  page; a remembered name a block lacks leaves its first variant
  selected. Other open tabs do not follow;
* `label="…"` to name the tablist for assistive technology (default
  "Example variants").

== `{{ variable }}` substitution

`{{ name }}` and `{{ name = default }}` tokens are found by a plain
regex in `tokenize()`. The block shows one labelled `<input>` per
variable name across **all** its variants, so a value typed once applies
everywhere the variable appears and survives switching variants. Typing
updates only the affected text in the code panel; the input keeps focus.

* A variable with a default shows the default (and uses it as the input
  placeholder) until the reader types.
* A variable with no default and no value shows `{{ name }}`, styled as
  unset.
* An empty value counts as unset: you cannot make a variable render as
  the empty string.

These are template variables, matched by a regular expression in
`tokenize()` (`src/prog-block.js`). No grammar or parser is involved:
A2ML, which the syntax was once attributed to, is retired, and the
unused parser stub was deleted on 2026-10-05.

From script: `block.getVariable(name)`, `block.setVariable(name, value)`,
`block.text` (the example exactly as the reader sees it), and
`block.refresh()` (re-read the authored content; see below). The block
dispatches `progblocks:variable-change` `{ name, value }` and
`progblocks:variant-change` `{ variant }`; both bubble and cross the
shadow boundary.

== Line numbers

Add the `line-numbers` boolean attribute to render a gutter:

[source,html]
----
<prog-block line-numbers>...</prog-block>
----

The gutter is `aria-hidden="true"` and `user-select: none`, and the Copy
button copies only the code, so line numbers never travel with the code.
There is **no UI toggle**; it is host-attribute-only.

== Do not expect while authoring

* No preview toggle and no templating wizards — never implemented.
* No inline code editing, linting, split view, smart paste or structured
  (JSON/CSV/Nickel) export — removed on 2026-10-05 as out of charter. See
  link:Feature-Status.adoc[Feature Status].
* No syntax highlighting — `language="…"` only adds a `language-…`
  class to `<code>` for a host highlighter.
* ~~No live updates from the light DOM.~~ Since 2026-10-05 the block
  watches its own children: adding, removing or editing templates or
  text re-renders it (once per burst of changes), keeping the selected
  variant and the reader's values. Two caveats: editing a template's
  `.content` fragment directly is invisible to observers, so call
  `block.refresh()` afterwards; and a re-render replaces the inputs, so
  a reader focused inside the block loses focus.
