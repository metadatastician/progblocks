[IMPORTANT]
====
`README.md` lists accessibility as "Implemented, not verified" with
an AA target. Read this as a target, not an achieved conformance level.
**The AAA conformance tier of WCAG is not met** by this component,
despite historic claims made about it elsewhere in the estate. Do not
repeat an AAA conformance claim for ProgBlocks anywhere — this
repository's `tools/check-wiki-health.sh` enforces exactly that by
grepping this wiki tree for the literal string that names WCAG's top
tier and failing if it finds one.
====

== What is actually present

Read directly from `src/prog-block.js` and `src/prog-block.css` as of
2026-10-05 (branch `feat/render-core-variants-vars`):

* **Tabs pattern.** With two or more variants: `role="tablist"` (named by
  the `label` attribute, default "Example variants"), `role="tab"` buttons
  with `aria-selected` and `aria-controls`, and a `role="tabpanel"` code
  panel whose `aria-labelledby` follows the selected tab. Roving
  `tabindex` gives the tablist a single tab stop; ArrowLeft/ArrowRight
  (wrapping), Home and End move and activate the selection (automatic
  activation). With one variant there is no tablist, and the code panel
  has `role="group"` and `aria-label` (the `label` attribute, default
  "Code example").
* **Labelled inputs.** Each variable input has a `<label for>`, inside a
  `<fieldset>` whose `<legend>` ("Customise this example") is visually
  hidden with `.sr-only`.
* **Live region.** A visually hidden `role="status"` region announces
  "Copied to clipboard", a copy-failure instruction, "Downloaded
  <name>", or a group-sync change: "Also switched 1 other example to
  Windows" in the block the reader used, or "Switched 2 examples to
  Linux to match another tab" when a choice made in another tab is
  followed. Programmatic and restored changes are not announced.
* **Keyboard access to long lines.** The code panel is focusable
  (`tabindex="0"`) so keyboard users can scroll it horizontally.
* **Line numbers** are `aria-hidden="true"` and `user-select: none`, and
  Copy never includes them.
* **Visible state without colour alone.** The selected tab is shown by an
  underline bar and font weight; the old `opacity: 0.7` on inactive tabs
  was removed. Unset variables are shown as `{{ name }}` in italic as well
  as colour.
* **Focus and high-contrast modes.** `:focus-visible` outline rings, and a
  `@media (forced-colors: active)` block that maps the selected-tab bar to
  `Highlight` and outlines variable values.

Structural parts of this (roles, `aria-controls`/`aria-labelledby`,
roving `tabindex`, arrow/Home/End keys, every input labelled, line
numbers hidden, the status message after copy) are asserted by
`tests/component.test.js`, under happy-dom.

== What is not verified

* **Screen-reader testing is partial.** The owner ran the script below on
  2026-10-06 and reported "it works, on read and write at least": reading
  the code and editing a variable pass. The other steps, and which reader
  and browser were used, are not yet recorded.
* **Automated audit, local and in CI.** `just a11y` (`tools/a11y-audit.mjs`,
  `CHROMIUM_PATH` required) runs axe-core with WCAG 2.0/2.1/2.2 A+AA and
  best-practice rules on `index.html` in headless Chromium, dark and
  light. On 2026-10-05: 0 violations, 0 needing review, colour contrast
  passing on 39 nodes; planted defects make it exit 1. CI's `build` job runs it on every
  push and pull request, against the runner's Google Chrome.
* **Contrast beyond the resting state is unmeasured** — hover and focus
  states, and any host override of the `--pb-*` colours.

== Known gaps

* ~~**Group-synced changes are not announced.**~~ — since 2026-10-06 the
  block the reader used announces how many other examples followed
  (RELEASE-CRITERIA A2). Because tabs activate automatically, each arrow
  key queues one polite announcement; whether that is chatty in practice
  is a question for the screen-reader run (step 8).
* ~~**Content changes after first connect are ignored**~~ — since
  2026-10-05 the block re-renders when its authored content changes
  (`DEBT.adoc` C14, cleared). The re-render replaces the variable
  inputs, so a reader focused inside the block loses focus when the host
  changes the content; this is host-driven and rare, and has not been
  checked with assistive technology. Edits to a template's `.content`
  still need `block.refresh()`.

The focus-loss defect that used to dominate this page — every keystroke
in a variable input destroyed and recreated the input — was fixed on
2026-10-05: the shadow tree is built once and patched in place (see
link:Architecture.adoc[Architecture]).

== Screen-reader test script

First run 2026-10-06 by the owner: steps 4 and 5 (edit a value, hear the
substituted code) and reading the code pass; the rest are unrecorded. It
is written so that one person with a
screen reader can run it in about 15 minutes and record a result. Use the
demo page (`index.html`, served over HTTP from the repository root) and
run it with at least *NVDA + Firefox or Chrome on Windows* and
*VoiceOver + Safari on macOS*. For each step, record pass, fail, or what
was actually announced.

. *Reach the first example.* Tab from the top of the page. Expected: focus
  lands on the selected tab, announced as a tab in the "Operating system"
  tab list, "1 of 3", selected.
. *Switch variants with the keyboard.* Press Right Arrow, then End, then
  Home. Expected: each key moves focus *and* selection; each tab is
  announced with its name, position and "selected". Left Arrow on the
  first tab wraps to the last.
. *Reach the code.* Press Tab from the tab list. Expected: focus moves to
  the code panel, announced as a tab panel labelled by the selected tab
  ("macOS" and so on). Reading its content should not include line numbers.
. *Edit a value.* Tab to the "package" field. Expected: announced as an
  edit field labelled "package", inside the group "Customise this
  example". Type `jq`. Expected: focus and caret stay in the field for
  every character.
. *Hear the substituted code.* Shift+Tab back to the code panel and read
  it. Expected: the line reads `brew install jq` (or the variant's
  equivalent), not `{{ package }}`.
. *Copy.* Tab to "Copy" and press Enter. Expected: "Copied to clipboard"
  is announced without moving focus.
. *Download.* Tab to "Download" and press Enter. Expected: "Downloaded
  example.txt" is announced.
. *Group sync.* Change the tab in the first example. Expected: after the
  tab, "Also switched 1 other example to <name>" is announced; the second
  example shows the same variant. Then press Right Arrow a few times and
  record whether one announcement per key is too chatty.
. *High contrast.* In Windows High Contrast (or forced colours), confirm
  that the selected tab and substituted values are still distinguishable.

Record results in `DEBT.adoc` T3. Only when every step passes on both
readers may AA move from "target" to "tested with assistive technology".

== Net assessment

ProgBlocks now implements the markup and keyboard behaviour that WCAG 2.1
AA and the ARIA Authoring Practices tabs pattern call for, and its
structure is unit-tested. That makes AA a credible *target*; it is **not**
a verified conformance level until it has been tested with a screen
reader; the automated audit and resting-state contrast check pass. AAA is not attempted and is not
met.
