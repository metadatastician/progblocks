= EXPLAINME — claim ↔ evidence traceability
:toc:

This document exists to be checked, not believed. For every substantive claim ProgBlocks makes about
itself, it gives the claim, the exact file/line that implements it, and the automated test or check
that evidences it — or states plainly "no automated evidence" where none exists. References into
`src/prog-block.js` are by function or method name, because that file was still being edited when
this was written (2026-10-05, branch `feat/render-core-variants-vars`); a line number is given only
where it is stable. If the source has moved, re-verify rather than trust this table.

Overall automated-test coverage (2026-10-06): `bun test` runs **81** tests in seven files, all passing.
`tests/component.test.js` (49) exercises the component's behaviour; `tests/property.test.js` (3) checks
`tokenize` and rendering over 500 seeded generated inputs each; `tests/registration.test.js` (1) asserts
the element registers; `tests/ci-config.test.js` (4) and `tests/dependabot-config.test.js` (2) guard CI
configuration; `tests/jcs.test.js` (10) and `tests/publish-wiki.test.js` (12) cover the tools. Every
component test runs under happy-dom (`tests/helpers/dom.js`), **not in a real browser**. All of `src/`
is now the component: the unimported stubs `src/a2ml-parser.js` and `src/k9-validator.js` were deleted
on 2026-10-05 and 2026-10-06.

== The component registers as a custom element

*Claim:* `<prog-block>` is a working custom element.

*Implementation:* `customElements.define('prog-block', ProgBlock)` — the last line of `src/prog-block.js`, guarded
so a second load does not throw.

*Evidence:* **Automated: `tests/registration.test.js`, passing.** History: before PR #18,
`src/prog-block.js` imported `{ validateK9 }` from `src/k9-validator.js`, which exports only
`K9Validator` and `defaultValidator` — a link-time ES module error that kept `customElements.define()`
from ever running. That was corrected, and since 2026-10-05 `src/prog-block.js` imports nothing at
all. Verify with `bun test`.

== Variant switching (tabs)

*Claim:* code blocks can offer multiple variants, switchable via a tab UI that follows the WAI-ARIA
tabs pattern.

*Implementation:* `_readLightDom()` in `src/prog-block.js` reads `<template data-variant="…">`
children. `_build()` creates a `role="tablist"` (named by the `label` attribute, default
"Example variants") with one `role="tab"` button per variant, each with `aria-controls` pointing at the
`role="tabpanel"` code panel. `_renderVariant()` sets `aria-selected`, a
roving `tabindex` and the panel's `aria-labelledby`. `_onTabKey()` handles ArrowLeft/
ArrowRight (wrapping), Home and End with automatic activation. The `variant` attribute/property
(`attributeChangedCallback`, `get`/`set variant`) selects the initial or current variant. With a single variant no tablist is built
and the `language` attribute is shown as a label instead (`_build()`, `_renderLanguage()`).

*Evidence:* **Automated, under happy-dom:** `tests/component.test.js` › `variant switching` —
`tabs follow the WAI-ARIA tabs pattern`, `arrow keys, Home and End move selection with wrap-around`,
`the variant attribute picks the initial variant`, `a single variant renders no tablist`. Tabs are
generic labels: there is no OS/shell/language semantics and no platform detection.

== Cross-block variant sync (`group`)

*Claim:* blocks sharing a `group` attribute switch variant together.

*Implementation:* a module-level `Map` of groups (`src/prog-block.js:13`); `_joinGroup()`,
`_leaveGroup()` and `_syncGroup()`. A user-initiated switch selects the same variant
*name* in every other block of the group that has one.

*Evidence:* **Automated, under happy-dom:** `blocks in the same group switch together; other groups do
not`. By default the selection is in memory only. Persisting it across page loads is opt-in with
`persist` (next section); `DEBT.adoc` C15 recorded its absence until 2026-10-05.

== Remembering the reader's variant (`persist`)

*Claim:* on a block with `group` and the boolean `persist` attribute, the variant the reader selects
is remembered across page loads in `localStorage` and restored ahead of the `variant` attribute. Only
reader-initiated selections are stored; blocked or unavailable storage degrades silently to
page-local group sync; a remembered name the block lacks falls back to the first variant. Without
`persist` nothing is stored. With `persist`, other open tabs of the same site follow through the `storage` event.

*Implementation:* `recall()` and `remember()` near the top of `src/prog-block.js`, both reading or
writing the key `progblocks:variant:<group>` (`STORAGE_PREFIX`) inside `try`/`catch`.
`connectedCallback()` calls `recall()` on first connect when `persist` and `group` are both set, and
prefers the result over the `variant` attribute; `_selectByName()` ignores a name the block lacks.
`_select()` calls `remember()` only on the `notify` path, i.e. for a reader-initiated change. `listenAcrossTabs()`
adds one `storage` listener that selects the new name in this tab's `persist` blocks of that group,
without notifying or writing back. Evidence adds `a choice persisted in another tab is followed here,
without echo` and `unrelated storage keys are ignored`; checked once by hand with two headless
Chromium tabs on 2026-10-05.

*Evidence:* **Automated, under happy-dom:** `tests/component.test.js` › `remembering the reader's
variant` — `persist stores a reader choice and restores it on the next page`, `without persist nothing
is stored`, `a remembered name the block lacks falls back to the first variant`, `blocked storage
degrades silently` (a `localStorage` getter that throws). Mutation-checked by hand on 2026-10-05:
removing the persist write failed 1 test. Not observed in a real browser.

== Authored content that changes after render

*Claim:* if the host adds, removes or edits the block's templates or text after it has rendered, the
block re-renders, keeping the selected variant (by name) and the reader's variable values.

*Implementation:* `connectedCallback()` attaches a `MutationObserver` to the host (`childList`,
`subtree`, `characterData`, and the `data-variant` attribute). `_scheduleRefresh()` coalesces a burst
of mutations into one `refresh()` per microtask. `refresh()` (public) re-reads the light DOM,
replaces the shadow tree via `_build()`, restores the variant by name (first variant if it is gone)
and writes the reader's values back into the new inputs. `disconnectedCallback()` disconnects the
observer. Limits: edits to a `<template>`'s `.content` fragment are invisible to observers, so the host
calls `refresh()` after one; a rebuild replaces the inputs, so focus inside the block is lost.

*Evidence:* **Automated, under happy-dom:** `tests/component.test.js` › `authored content that changes
after render` — `replacing templates re-renders, keeping the variant and reader values`, `editing
plain-text content is picked up`, `refresh() picks up edits inside template.content`, `a burst of
mutations triggers one rebuild`. Mutation-checked by hand on 2026-10-05: disabling the observer failed
3 tests. Not observed in a real browser.

== Variable substitution

*Claim:* `{{ name }}` and `{{ name = default }}` placeholders in variant content are bound to
reader-editable values.

*Implementation:* `tokenize()` (pattern `VAR_PATTERN`, `src/prog-block.js:9`) splits each variant into
text and variable segments. `_readLightDom()` collects every variable across all variants with its
default. `_build()` creates one labelled `<input>` per variable inside a `<fieldset>`
with a visually hidden legend. `setVariable()` stores the value and updates
only the matching `<span>` nodes in the code panel (`_renderValues()`). An unset variable
with no default shows as `{{ name }}` with class `unset`. API: `getVariable()`,
`setVariable()`, and the `text` getter, which returns the personalised example.

These are template variables, matched by a regex; no grammar or parser is involved.

*Evidence:* **Automated, under happy-dom:** `tests/component.test.js` › `variable substitution` —
`unset variables keep their placeholder visible`, `inline defaults fill the example and the input
placeholder`, `values persist across variant switches and one input serves all variants`, `every
input has an associated label`; and `tokenize separates text and variables with defaults`.

Deliberate behaviour, not a defect: an empty value means "not set", so the default (or the
placeholder) is shown. A variable cannot be set to the empty string (`DEBT.adoc` C4).

== Editing a variable value updates the code live

*Claim:* typing into a variable's `<input>` updates the rendered code in place without losing focus.

*Implementation:* the input's `input` listener calls `setVariable()` (wired in `_build()`), which
patches text nodes only. The shadow tree is built once (`_build()`, guarded by `_built` in `connectedCallback()`) and
is rebuilt only when the authored content changes (see above), never in response to typing, so the
focused `<input>` is not replaced while the reader types.

*Evidence:* **Automated, under happy-dom:** `typing keeps the same input element and updates the code
in place` (asserts the same node identity before and after input). Not observed in a real browser.

== Copy to clipboard

*Claim:* the Copy button copies the example exactly as the reader sees it, with their values
substituted, and announces the result.

*Implementation:* `_copy()` writes `this.text` via
`navigator.clipboard.writeText` and calls `_announce()`, which writes to a
`role="status"` region created in `_build()`. On failure it announces a manual-copy instruction.

*Evidence:* **Automated, under happy-dom, with `navigator.clipboard` stubbed:** `copy writes the
personalised text and announces it`. The failure path has no test.

== Events

*Claim:* the block emits `progblocks:variant-change` `{ variant }` and `progblocks:variable-change`
`{ name, value }`, both bubbling and composed.

*Implementation:* `setVariable()` (variable) and `_select()` (variant), in `src/prog-block.js`. The variant event
fires only for a change the reader makes in this block, not for programmatic or group-synced changes.

*Evidence:* **Automated, under happy-dom:** `emits progblocks:variable-change` and `emits
progblocks:variant-change for reader selection only`.

== Export to file

*Claim:* a Download button saves the personalised example as a plain-text file. The JSON, CSV and
Nickel formats were removed on 2026-10-05; their "CSV" and "JSON" were not real encodings
(`DEBT.adoc` C8).

*Implementation:* `_download()` in `src/prog-block.js` builds a `text/plain` `Blob` from `text`, names
it from the `filename` attribute (default `example.txt`, path and reserved characters replaced by
`_`) and clicks a temporary `<a download>`, then announces the result in the status region.

*Evidence:* `tests/component.test.js` — "download saves the personalised text under the filename
attribute".

== Clipboard-safe line numbers

*Claim:* line numbers are visible but excluded from copy-paste and from assistive technology.

*Implementation:* the gutter is `aria-hidden="true"` (set in `_build()`) and
`user-select: none` (`.line-numbers` in `src/prog-block.css`); `_renderLineNumbers()`
matches the active variant's line count. The Copy button copies `text`, which never includes them.
Controlled by the `line-numbers` host attribute; there is no UI toggle.

*Evidence:* **Automated, under happy-dom:** `line numbers match the line count and are hidden from
assistive tech`. No test asserts the computed `user-select` style or a manual selection.

== Accessibility

*Claim:* WCAG 2.1 AA *target* for interactive elements. A target, not a verified level.

*Implementation present:* the WAI-ARIA tabs pattern (see Variant switching); one `<label>` per variable
input inside a `<fieldset>` with a `.sr-only` legend; a `role="status"` live region for copy
and download results; a single-variant code panel with `role="group"` and an `aria-label`; a focusable code panel (`tabindex="0"`) so keyboard
users can scroll long lines; `aria-hidden` line numbers; `:focus-visible` rings
(`src/prog-block.css`); selection shown by an underline bar and weight rather than colour
or opacity (`.tab[aria-selected="true"]`); a `@media (forced-colors: active)` block.

*Evidence:* **Structure automated, under happy-dom:** the tabs-pattern, label and line-number tests
above. **Automated audit in a real browser:** `just a11y` (`tools/a11y-audit.mjs`) runs axe-core with
the WCAG 2.0/2.1/2.2 A and AA and best-practice rules against `index.html` in headless Chromium, dark
and light colour schemes: 0 violations, 0 needing review, colour contrast passing on 39 nodes
(2026-10-05; the demo now uses `persist`). Planted defects (an unnamed button, a 1.5:1 colour pair) make it exit 1. It is not in
CI and needs a local Chromium. **Not verified:** no screen-reader session; axe sees the default
palette in its resting state only, not hover/focus states or host overrides. The live region announces
copy and download results only; a variant change caused by `group` sync in
another block is not announced. See `DEBT.adoc` T3.

*Implementation:* none. Template variables (`{{ name }}` / `{{ name = default }}`) are a regex in

planned.

*Evidence:* `test ! -e src/a2ml-parser.js && test ! -e assets/tree-sitter-a2ml.wasm` (the Dust
contractile's `a2ml-parser-stub` and `wasm-placeholder` probes, `just probes`).

== Escaping / sanitising untrusted content

*Claim:* author content and reader input are rendered as text, never as markup.

*Implementation:* the shadow tree is built with `createElement` and every text value goes in through
`textContent` (`el()`, `_renderVariant()`, `_renderValues()` in `src/prog-block.js`). Variant source is read with `template.content.textContent` (`_readLightDom()`), so tags written
unescaped inside a `<template>` are dropped rather than rendered; authors escape `<` and `&` as they
would inside `<pre>`. There is no `innerHTML` in `src/` (`grep -n innerHTML src/` → only the explanatory
comment near the top of `src/prog-block.js`). No sanitiser is used, because nothing is parsed as markup.

*Evidence:* **Automated, under happy-dom:** `tests/component.test.js` › `untrusted content is never
rendered as markup` — escaped markup in a variant, unescaped markup in a template, markup typed into a
variable input, and markup in a tab label. Not tested in a real browser and not independently
reviewed.

== Stylesheet loads correctly wherever the component is embedded

*Claim:* the component's styling works regardless of where the host page lives.

*Implementation:* the stylesheet URL is `new URL('./prog-block.css', import.meta.url)`
(`STYLESHEET_URL`, `src/prog-block.js:10`), appended once as a `<link>` in the shadow root by
`_build()`. It resolves
against the module, so the host page can live at any depth.

*Evidence:* **Automated, under happy-dom:** `stylesheet resolves against the module, not the host
page`, mounted on a page at `/docs/deep/page.html`. Not yet checked in a real browser at a non-root
depth.
